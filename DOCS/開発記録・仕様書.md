## 0. 最初に読む人へ（3分で全体像）

**SEIKA＋は、青果センターの在庫を全員が同じ画面で見て、仕入れ担当者への過不足連絡を自動化するために作った社内アプリです。** 現在は石岡青果センターに加えて、本社工場の入荷・在庫・下処理にも使っています。

技術的には、次の3つを押さえれば動きが分かります。

1. **画面は素のHTML/CSS/JavaScript**です（フレームワーク・ビルドなし）。`index.html` は外枠だけで、処理は `js/01〜26` を**番号順に読み込み**ます。後の番号のファイルが前の関数を上書きすることがあります。
2. **データはSupabase（PostgreSQL）**にあります。石岡の通常在庫は `app_state` の1行JSONに入っています。QRロット・品質評価・棚卸し・本社などは、専用テーブルとRPC（DB内の関数）で扱います。権限はDB側で確認します。
3. **公開はGitHub Pages**です。`kk-seki/seika-plus` の `main` にマージされると、そのまま本番に出ます。

**引き継ぎで一番ハマるのがこれです。**

> 関数名・RPC名・テーブル名に付いている `v188` `v1159` `v1500` `v1199c117` などは、**その機能が入った版の番号**です。
> 古い世代も消さずに残っています。さらに、後から読み込むファイルで `window.〜` を差し替えている箇所が多くあります。
> **直す前に必ず `js/` 全体を検索して、最後に有効になっている定義を特定してください。**（詳細は 5.1）

## 1. アプリの目的と概要

### 1.1 なぜ作ったか（当初の課題）

開発の出発点は、2026-07-08 のこの一言でした。

> 「作りたいのは在庫管理についてで、適正在庫を設定して過不足があるとLINEと連動して仕入れ担当者に連絡が行くシステムを作りたい。」

| 当時の課題 | 具体的に何が問題だったか |
|---|---|
| 連絡のタイムロス | 仕入れ担当への在庫過不足の連絡を、毎回LINEに**手打ち**していた |
| 抜け漏れ | 手打ちだと「多い／少ない」の品目が抜ける |
| 個人差 | 判断する人によって報告内容がばらつく |
| 判断の不安 | 仕入れ担当者が在庫の実態を確認できず、発注判断が読みになる |
| 費用 | 既存の有料システムの月額費用を抑えたい |

**このアプリの目的は「在庫を記録すること」ではなく、「仕入れ判断に必要な情報を、抜けなく・個人差なく・すぐ届けること」です。** 記録は手段です。機能を足すかどうかは、この目的に照らして判断してください。

### 1.5 設計判断の記録（なぜこうなっているか）

**ここを知らずに"改善"すると、過去に解決した問題を再発させます。**

| 判断 | 採用した形 | 見送った案と理由 |
|---|---|---|
| 石岡の通常在庫 | **今ある数を直接入力**（入れ数×ケース数＝kg）。出庫は記録しない | 入出庫の積み上げ。現場が「今ある数を入れる方が早い」と判断。差し引き管理はQR在庫が担う |
| LINE連絡 | **アプリが報告文を作る→人がLINEへ貼る** | 完全自動送信。LINE Notify終了済みで、サーバー常設の費用・保守が増えるため |
| データ保存 | **Supabase（クラウド）** | 端末内保存では全員が同じ在庫を見られない |
| 通常在庫の持ち方 | **`app_state` の1行JSON** | 正規化。改版速度を優先した（4.3のトレードオフあり） |
| 業務ロジックの置き場所 | **できるだけDBのRPC側** | JS側だけだと画面を書き換えて迂回できる |
| 認証 | **Supabase Auth**。ログイン画面は名前を選んでパスワード入力 | 当初はアプリ独自の `users` 管理だったが、v1.199〜で本人トークン方式へ移行。現場にメール運用がないため、名前選択の形は維持 |
| 本社下処理班 | **共用アカウント＋入力者のサイン必須** | パートさんに個別アカウントを作らない運用のため、誰が入力したかはサインで残す |
| フレームワーク | **使わない** | ビルド環境が必要になり、保守が難しくなるため |
| 古い関数の扱い | **すぐには消さない**。整理は検索で「呼ばれていない」と確かめてから | 稼働中の業務を止めないことを優先 |

### 2.3 読み込みの順番と上書き

- `js/` は `index.html` に書かれた順（01→26）で読み込まれます。
- 後のファイルが `window.〇〇=…` で前の関数を差し替えるため、**同じ名前の関数でも、最後に読み込まれた定義が有効**です。
- 2026-11 の整理で重複定義は大きく減りましたが、なくなってはいません（2026-11-19 時点で、エラーを黙って握りつぶす `catch(e){}` が約170か所、`MutationObserver` が15か所あります）。

## 3. 主要な機能一覧

### 3.1 役割（権限）

全11役割です。ホーム画面は役割ごとに変わります。**画面の出し分けは見た目だけで、実際の権限はDB側で確認します。**

|---|---|---|---|
| 石岡 | `admin` | 管理者 | 全機能。ユーザー管理、確定・削除、価格設定 |
| 石岡 | `worker` | 青果社員 | 通常在庫・QR在庫・廃棄・棚卸し・品質評価の入力。品目設定・仕入れ担当者の変更 |
| 石岡 | `buyer` | 仕入れ担当者 | 発注判断、適正在庫（週次見直し）、低評価の確認。QRと廃棄は閲覧 |
| 石岡 | `sales` | 営業担当者 | 在庫確認、廃棄単価・金額管理 |
| 石岡 | `clerk` | 事務員 | 廃棄記録、単価、Excel作成 |
| 石岡 | `viewer` | 閲覧者 | 在庫・QRロット・廃棄一覧の閲覧 |
| 石岡 | `office_viewer` | 総務（閲覧） | 閲覧 |
| 本社 | `hq_worker` | 本社社員 | 受け入れ・確定、下処理の確認・確定・訂正、在庫入力、棚卸し、マスタ・スタッフ登録、集計・Excel |
| 本社 | `hq_clerk` | 本社事務 | 本社の在庫・集計の閲覧、Excel |
| 本社 | `hq_receiver` | 本社 荷受け担当者 | 品質評価と確定、貼り紙の印刷、在庫入力、原料出し・下処理への出庫 |
| 本社 | `hq_prep` | 本社 下処理班 | 下処理と作業時間の記録（共用アカウント・サイン必須）。金額は表示しない |

役割ごとの詳しい操作は、アプリ内の「操作ガイド」と「権限別操作マニュアル」（PDF、全11役割）を参照してください。
トレース表は、本社の下処理班と荷受け担当者には表示しません（`db/040`）。

### 3.2 機能一覧（石岡）

| 分類 | 機能 | 概要 |
|---|---|---|
| 在庫 | 通常在庫入力 | 品目ごとに入れ数×ケース数。同じ品目で複数の入れ数に対応 |
| 在庫 | 在庫表・印刷 | 第2冷蔵庫／第3冷蔵庫／その他（片岡）。QR品目もkgで1つにまとめ、在庫のある品目だけをA4に自動で収める |
| 在庫 | 特殊在庫 | 鉄コンテナ・網コンテナ・パレット。**網コンテナは種類の追加・名称変更・使用停止が可能**（c127） |
| 判定 | 発注候補・過多品目 | 適正在庫と比べる。QR品目も含めて表示 |
| 判定 | 適正在庫の週次見直し | 仕入れ担当者が見直し、記録と変更履歴を残す（`db/037・038`） |
| 連絡 | 在庫報告コピー | 「過多」「不足」を文章にしてLINEへ貼る |
| QR | ロット登録・QR貼り紙 | 1パレット/ケース数の表記、規格別ロット。**仕入先・単協名はマスタの正式名から選ぶ**（マスタにない名前は確認して登録。別名は自動で正式名に直す）（c130） |
| QR | 仕入先・単協マスタ | 正式名・別名・非表示。管理者は、ロットに入っている表記を正式名にまとめ、過去のロット・履歴・本社入荷記録の表記も直せる（`db/052`、c130） |

**本社 下処理の流れ（c116〜c126）**

1. 作業開始：仕掛品を選ぶ（同じ品目なら複数選択可。マスタにないものは手入力可）。スタッフは班ごとに折りたたんだ一覧から複数選択。
2. 使用原料：1パレット・1基ずつQRを読み、「全量使った／半端が残った」を選ぶ。全量ならkgを自動で入れる（ケースは量目×ケース数、大型容器はその1基のkg）。半端なら残りのkgを入れる。
3. 休憩・中断：休憩に入らない人を選べる。あとから休憩の追加、抜けた・入った時刻の修正ができる。
4. 終了：入力内容の確認画面を1回挟み、入力者がサインする。
5. 社員の確認：本社社員・管理者が確定する。不備があれば訂正するか、下処理班に差し戻す。確定後も社員は時刻を訂正できる。
6. 廃棄は「使用原料－出来高」の自動計算を初期値にし、手入力で直せる。仕掛品の使用期限は2日。清掃は日報に入れない。
7. 端末を取り合うため、日報はあとから入力できる。確定前の作業は、下処理班・本社社員・管理者が削除できる。

### 4.3 `app_state` 方式の注意

石岡の通常在庫は、正規化されたテーブルではなく**1つのJSON**です。

- 利点：スキーマ変更なしで項目を足せる。
- リスク：後勝ちで上書きすると他人の更新が消える。そのため **`update_app_state_if_version_v187`（版番号の照合）** で保存します。
- 保存は「端末のキュー → 少し待って送信」の流れで、成功の条件が複数あります。保存・同期を触ったら、必ず `tests/sync.py` を含む全体チェックを回してください。
- 未同期のデータは、再入力せず同じ端末から再送します（画面上部が「クラウド保存済み」になることを確認）。

> **過去の重大事故（v1.192で修正）**：保存データを組み立てる処理が、条件によって棚卸しデータを削除していました。**`app_state` へ保存する処理を変えるときは、その役割が触っていない領域を落としていないか必ず確認してください。**

### 4.4 月末棚卸し

対象月末の在庫をスナップショット → 実数を入力（QRはスキャン） → 差異の理由を入れて確定 → 差異だけを月末日付で履歴へ反映 → Excel出力（デスクネッツ文書管理へ保管）。差異ゼロでも確定できます。確定後の修正は管理者が差分を追加します。

### 4.5 容量とバックアップ

Supabase無料枠：DB 500MB・Storage 1GB・転送5GB/月。

- 2026-08-31 に旧バックアップ方式（`app_state_backups`）の肥大でDBが238MBになり、整理と `vacuum (full, analyze)` で32MBまで減らしました。
- その後、自動バックアップの保存期間と詰め直し（`db/030・031`）、通信量を減らす改修（`db/014・015`）を入れています。
- **現在の容量は本書では未確認です。** 月1回、Supabase の Usage 画面で確認してください。

## 5. 今後のメンテナンス・修正時の注意点

### 5.1 ★最重要：版番号つきの名前と上書き

```
v188Home / v192DownloadExcel                     ← JS側（v1.88、v1.192で追加）
list_qr_quality_evaluations_v1102 → _v1159       ← RPC（作り直すたびに番号が増える）
hq_works_v1500 / hq_work_pauses_v1199c116        ← 本社のテーブル（版＋作業番号）
```

**必ず守る手順：**

1. 直したい機能の名前で **`js/` 全体を検索**する（`grep -rn 名前 js/`）。
2. 同じ系統の関数が複数あれば、**最後に読み込まれるファイル**と `window.〜` への代入を確認し、実際に有効な定義を特定する。
3. その定義だけを直す。古い世代は、呼ばれていないと確かめるまで消さない。
4. RPCは `db/` の後の番号のSQLで作り直されていることがある。**最新の番号の定義**を見る。

### 5.2 納品（リリース）の手順

1. 最新の `main` からブランチを作る（例：`c128-内容`）。
2. 修正する。機能を足したり変えたりしたら、**アプリ内の操作ガイドも更新**する。
3. `sw.js` のキャッシュ名を上げる（`-c127-r1` → `-c128-r1` など）。版番号 v1.199 は指示がない限り変えない。
4. `python3 tests/run_all.py` を実行し、すべて成功することを確認する。
5. 1コミット（題名「v1.199-cNN 内容」）にまとめ、`main` 宛てのPRを作る。
6. DBの変更があるときは、`db/` に次の番号でSQLを入れ、`db/README.md` に「SQLが必要か／実行する順番／成功の確かめ方／保管名」の4点を書く。SQLは `BEGIN; … COMMIT;` で包み、末尾で成功確認（`OK` 表示）をする。
7. **平田さんがSQLを本番で実行 → 成功を確認 → PRをマージ**（この順番）。
8. GitHubの「自動チェック」と Pages 公開が緑になったことを確認し、実機で開いて確認する。

> 自動チェックは、PRの段階で準備（Playwrightのインストール）に時間がかかり、15分の上限で止まることがあります。その場合はコードの失敗ではないので、「Re-run jobs」で再実行してください。

### 5.3 やってはいけないこと

| やってはいけない | 理由 |
|---|---|
| `app_state` をSQLで直接UPDATEする | 版番号の照合を迂回し、他の人の更新を消す |
| 印刷用HTMLの中に `<script>` を書く | 閉じタグが本体のJavaScriptを途中で終わらせ、画面にコードが出る |
| 権限や在庫計算をJS側だけで行う | 画面を書き換えれば迂回できる。DB側で確認する |
| `sw.js` のキャッシュ名を変えずに公開する | 利用者に更新が届かない |
| 石岡の通常在庫に出庫機能を足す | 通常在庫は「今ある数」を入れる方式。差し引きはQR在庫の役割 |
| トリミングで在庫を減らす | トリミングは歩留まりの記録 |
| 現在庫を超える出庫を許す | DB側で禁止している。迂回しない |
| 大量削除の後にVACUUMを省く | 容量が戻らない |
| 認証情報（秘密キー・パスワード）をコードやチャットに書く | GitHubの履歴・チャット記録に残る |
| 古い世代の関数をまとめて削除する | どこから呼ばれているか確かめずに消すと、特定の操作だけ壊れる |

- 更新するとき：テーブル・RPC・画面・役割・運用ルールを追加・変更したとき。
- 記載と実体が違ったら、**実体が正**です。本書を直してください。

**まだ載っていない領域（今後追記）**

- Web Push の鍵・Edge Function の設置場所と更新方法（要確認）
- RLSポリシーの一覧と、各テーブルの想定アクセス範囲
- 現行世代のRPCの一覧（引数・戻り値）
- 障害時の連絡と復旧の手順（バックアップからの戻し方）
- `release-notes.json` と `index.html` の `<title>` が古いままの件（直すかどうか要判断）
